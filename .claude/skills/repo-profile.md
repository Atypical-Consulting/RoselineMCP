| `website/src/data/tools.ts`, `website/src/pages/tools.astro` | every tool change edits the public reference | **union** entries |
| `website/package-lock.json` | lockfile churn | **regenerate** (`npm install` in `website/`), never hand-merge |
| `RoselineMCP.sln`, `*.csproj` | both sides add files/packages | **union** item groups |
| Test files under `RoselineMCP.Tests/` | both sides append tests | **union** |
- **Rule of thumb:** union additive files, regenerate derived files, take-the-higher for the version;
  same-logic-both-sides is a real semantic conflict — understand both intents or stop.

## Architecture grain / invariants (shape implementation plans to these)
- **Doc alignment is a hard gate** (`CLAUDE.md`): a code change is not done until every mirroring
  surface is updated in the *same* change — `docs/API.md`, `CLAUDE.md`, `README.md`,
  `website/src/data/tools.ts` + `website/src/pages/tools.astro`, `mcpb/manifest.json`, `CHANGELOG.md`.
- **Read-only by default:** the navigation/diagnostics/patch tools never touch disk; the three write
  tools (`ApplyFixes`, `EditMember`, `RenameSymbol`) require an explicit `previewOnly: false`.
- **Typed envelope:** every tool returns `ToolResult<T>` (`{ ok, data, error }`) with
  `UseStructuredContent = true`. Tools **never throw to the MCP layer** — classify via
  `ToolExecutionHelper.Error<T>` and return the failure envelope.
- **Touch layers in order:** `Interfaces/` → `Services/` → `Tools/` → `Models/` → `RoselineMCP.Tests/`
  (the test project mirrors the main project's structure), then the doc surfaces above.
- **Stderr logging only** — stdout is the MCP stdio channel; anything written there corrupts the protocol.
- **Configuration is read once at startup** from `AppContext.BaseDirectory` (never the process cwd),
  env prefix `ROSELINE_`; no reload-on-change watchers.
- **`WorkspaceCache = false` does not save memory** — measured 2026-07-25 (+26% resident, ~45× second-call
  latency). Do not re-propose idle-release without reading `docs/ARCHITECTURE.md` § Memory Management.
- **Release is tag-driven:** never `dotnet nuget push` or create a GitHub Release by hand — the
  `publish-nuget.yml` workflow owns both. See `CLAUDE.md` § Releasing a New Version.

## Worktree home
- `.claude/worktrees/` — **verified ignored** once the `.gitignore` rule below is in place.
  At generation time `worktrees-ignored.sh` exited **1** for both `.claude/worktrees/` and
  `.worktrees/`; the fix (`.gitignore` entries for both) shipped alongside this profile. A worktree
  left in an unignored home is staged by any stray `git add -A` as a `160000` gitlink pointing at an
  unfetchable commit (#43), and `implement-issue`/`merge-pr` refuse to use one until the rule exists.
  ⚠️ Keep the rule **narrow** — a blanket `.claude/` would also hide this profile from git (guard exit 2).

## Environment gotchas
- **Claude Code sessions are worktree-isolated in this checkout.** A session launched in
  `.claude/worktrees/<name>` is refused any git operation targeting the shared checkout — including
  `cd <repo-root> && git …` and `git -C <repo-root> …`, and any command the harness deems too complex
  to prove stays inside the worktree (pipelines, redirects, heredocs). Run git from the session's own
  worktree; `git worktree add` from there *is* permitted, so per-issue worktrees still work.
- Use `git -C <path>`, not `cd <path> && …` — a `cd` in a compound command is reset between calls.
- The default branch is **`dev`**; open PRs with `gh pr create --base dev`. Defaulting to `main`
  targets the wrong branch.
- No `packages.lock.json` in the repo (CI caches `~/.nuget/packages` directly) — do not add one
  casually; `setup-dotnet`'s `cache: true` is deliberately unused because it requires lock files.
